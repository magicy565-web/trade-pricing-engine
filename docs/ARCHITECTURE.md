# 架构与设计约束

## 模块边界

`Worker → stdio MCP（仅 agent 凭据）→ 认证 HTTP → 领域服务 → SQLite`。

`企业管理人员 → 本地网页/企业入口 → 认证 HTTP → 相同领域服务`。

没有第二套模型循环，没有自动浏览器，没有运行任意脚本或读取任意路径的工具。成本与政策属于业务事实，不属于模型可自行写入的“记忆”。企业档案、邮箱、Shopify、原供应商报价入口均不被这个仓库修改。

## 计算边界

当前为单 SKU / 单订单数量 / 单目标币种。每项成本是 `per_unit` 或 `fixed`；单位必须完全一致，不自动将件、米、公斤相互换算。多个同类别的 BOM 组件可相加；`covers` 声明包装/运输已包含于打包价，阻断再加同类别独立费用。

费用只有 `payer=seller` 进入出口企业的报价成本。所有以销售收入为基数的费用汇总在已确认政策的 `revenue_fee_rate` 中；不能把佣金写为普通百分数金额。税务口径只接受企业财务已经确认的 `net_nonrecoverable_confirmed`：可回收税额不重复计为最终成本，未确认退税收益不自动冲减。系统不决定具体税收资格或税率。

原币成本 × 数量（仅 per_unit）× 显式换汇率，得到未舍入目标币种成本；汇率方向固定为 `1 source_currency = rate target_currency`。先加总未舍入成本，再按目标币种货币精度四舍五入。单价保留企业政策指定的 2–6 位小数。

设 C 为与收入无关的已核实订单成本，f 为销售收入比例费用率，m 为目标贡献率，Q 为数量：

`required_revenue = C / (1 - m - f)`

`candidate_unit_price = ceil(required_revenue / Q, policy_unit_precision)`

实际销售额先按货币精度舍入，比例费用再按销售额计算、舍入；引擎核对最终贡献率是否仍满足底线，必要时上调一个保守价格增量。这里返回的是**保守舍入后的政策底价**，不声称求得离散舍入系统里的数学全局最低价。

`order_contribution = revenue - known_order_cost - revenue_fee`。

`contribution_margin = order_contribution / revenue`。它不是加价率，也不是会计净利润。管理费用、所得税或融资费只有在财务确认并明确归属到本订单后才纳入成本；引擎不猜遗漏费用。

## 场景比较不是“凭空找最优方案”

用户/Worker 提供候选数量、销售价格、条款、地点、运输方式和付款条件。每个场景必须引用自己的已确认成本快照，成本快照覆盖实际数量范围和商业条件。引擎比较这些离散方案，不生成虚构批量折扣、不自行延长工厂交期承诺。

选择方案后须把实际案件更新到相同条件再计算并审核，比较页面本身不能成为正式报价。

## 核心记录

- `cases`：企业实际询盘与单调增加的版本。
- `snapshots`：已确认、带来源的成本/汇率/政策；保存内容哈希与确认人，只可撤销，不能覆盖。
- `quotes`：包含案件、全部输入快照、明确时钟、规则版本、金额结果的不可变内容；状态/版本单独保存。
- `approvals`：审批角色、内容哈希、意见、时间。
- `idempotency`：同企业、同操作者、同 request_id 保证同输入返回同结果；异输入返回 409。
- `audit`：事务内附加的事件哈希链。

没有引入新任务队列；报价是同步确定性计算，长任务交给宿主。所有变更事务使用 `BEGIN IMMEDIATE`；SQLite WAL 与有界 busy timeout 支持同实例下并发请求。此实现不是分布式数据库或跨主机队列。

## 状态

`draft → pending_approval → approved → issued`，或 `pending_approval → rejected`。

`needs_evidence`、`blocked`、`calculated` 是计算结果状态，不混作发送/订单状态。已批准内容永不被静默改写。任何案件版本变动会使旧报价不能继续审批/定稿；成本/汇率依据撤销、政策更换、有效期到期也会阻断。拒绝之后需重新计算成新的报价版本，不覆盖原始拒绝记录。

`issued` 是本系统内部定稿而不是外发回执。已导出的客户文件无法在客户设备上远程撤回，后续变更必须由企业通知对方。

## 历史重放

`replay_quote` 使用原案件、成本、汇率、政策以及当时 `calculated_at` 重算，比较完整结果哈希。历史计算相同不意味着今天可以继续签发，当前有效性须另行检查。未来引擎版本变更需要归档匹配的旧版本重放。

## 一期明确不做

多 SKU 订单成本分摊、信用评级/坏账概率、利润最大化自动谈判、实时税费/运价数据采购、国内外发票处理、自动退税、套期保值、跨租户模型 Shell 隔离、企业 SSO、公共买家认证、自动邮件发送。DDP 的正式签发也不开放。

## 为什么使用 Python 而不是先前讨论的 TypeScript

设计目标是确定性业务服务而不是替换 OpenMausBot。Decimal 和 SQLite 标准库降低了自行实现金额算法的风险；FastAPI 可直接生成强类型合同接口。SDK/运行时被隔离在边界，未来增加 TypeScript 客户端无需重写核算核心。
